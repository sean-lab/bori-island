Chapter 7 · Input, state machines, juice, debugging

돌아가는 게임에서 손에 붙는 게임으로

From a game that runs to a game that feels right

작동하는 게임과 재미있는 게임 사이에는 작은 기술이 많다. 입력을 프레임 단위로 다루기, 캐릭터를 상태 기계로 정리하기, 손맛을 더하는 연출, 버그를 잡는 디버그 화면, 그리고 장면 전환과 저장.

Between a game that works and a game that's fun lie many small techniques: handling input frame by frame, organizing a character as a state machine, adding juice, building a debug view to catch bugs, and switching scenes and saving.

7.1입력: 눌림, 유지, 뗌Input: pressed, held, released

키보드 이벤트는 아무 때나 도착한다. 게임은 업데이트를 시작할 때 한 번 키 상태를 찍어 두고 지난 프레임과 비교한다. 지금 눌려 있고 전에는 아니었으면 '눌림', 반대면 '뗌'이다. 점프는 '눌림'에, 달리기는 '유지'에, 가변 점프는 '뗌'에 반응한다. 키 이름 대신 점프, 던지기 같은 '행동' 이름으로 바꿔 두면 키 설정이나 게임패드, 터치 버튼을 붙이기 쉽다.

Keyboard events arrive whenever they like. The game takes one snapshot of the keys at the start of each update and compares it with the previous frame. Down now but not before means "pressed"; the reverse means "released." Jumping reacts to pressed, running to held, and the variable jump to released. Mapping keys to actions such as jump and throw, instead of key names, makes it easy to add key remapping, a gamepad, or touch buttons later.

7.2상태 기계란 무엇인가What a state machine is

상태 기계(정확히는 유한 상태 기계, FSM)는 세 가지로 정해진다. 있을 수 있는 상태의 목록, 들어올 수 있는 입력의 목록, 그리고 "이 상태에서 이 입력이 오면 다음 상태는 이것"이라는 전이 규칙이다. 기계는 어느 순간이든 정확히 한 상태에 있고, 입력이 올 때마다 규칙을 보고 다음 상태로 옮겨 간다. 기억하는 것은 '지금 상태' 하나뿐이다.

컴퓨터 과학 교과서에 자주 나오는 예는 지하철 개찰구다. 잠겨 있을 때 동전을 넣으면 열리고, 열려 있을 때 밀고 지나가면 다시 잠긴다. 잠긴 개찰구를 밀어 봐야 그대로 잠겨 있고, 열린 개찰구에 동전을 더 넣어도 열린 채 그대로다. 버튼으로 입력을 넣어 보자.

A state machine (strictly, a finite state machine, or FSM) is defined by three things: a list of possible states, a list of possible inputs, and transition rules of the form "in this state, on this input, go to that state." At any moment the machine is in exactly one state, and each input moves it to the next state according to the rules. The only thing it remembers is which state it is in.

The classic textbook example is a subway turnstile. When it's locked, a coin unlocks it. When it's unlocked, pushing through locks it again. Pushing a locked turnstile leaves it locked, and more coins in an unlocked one leave it unlocked. Use the buttons to send it inputs.

그림(상태 전이도)과 표(상태 전이표)는 같은 규칙을 다르게 적은 것이다. 코드로 옮길 때는 표를 그대로 자료구조로 쓰면 된다. 동작을 바꾸고 싶으면 표만 고치고, 표에 없는 조합은 처음부터 일어날 수 없다.

The diagram (a state diagram) and the table (a transition table) are two ways of writing the same rules. In code you can use the table itself as a data structure. To change the behavior you edit the table, and a combination that isn't in the table can't happen at all.

플래그 여러 개 대신 상태 하나One state instead of many flags

상태 기계 없이 캐릭터를 짜면 보통 참·거짓 변수(플래그)를 하나씩 늘려 간다. isJumping, isFalling, isStumbling, isDead. 플래그가 네 개면 조합은 2⁴ = 16가지인데, 실제로 말이 되는 조합은 다섯 가지뿐이다. 나머지 열한 가지는 '죽었는데 점프 중' 같은, 일어나면 안 되는 상태다. 코드 어딘가에서 플래그 하나를 끄는 것을 잊으면 바로 그 상태가 된다.

상태 변수 하나(state = 'jump')로 바꾸면 한 번에 한 상태만 가질 수 있으니 이런 조합은 아예 적을 수가 없다. 버그가 생길 자리를 구조로 막는 셈이다. 아래에서 플래그를 켜고 꺼 보자.

Without a state machine, a character usually grows a pile of true/false variables, or flags: isJumping, isFalling, isStumbling, isDead. Four flags allow 2⁴ = 16 combinations, but only five of them make sense. The other eleven are states that must never happen, like "dead but jumping." Forget to clear one flag somewhere in the code and you're in one of them.

Replace the flags with a single state variable (state = 'jump') and the character can only be in one state at a time, so those combinations can't even be written down. The structure itself rules the bug out. Toggle the flags below.

게임 밖의 상태 기계State machines outside games

상태 기계는 게임보다 훨씬 넓게 쓰인다.

  • 문자열 처리. 정규 표현식은 상태 기계로 바꿔 실행할 수 있다. 컴파일러에서 소스 코드를 단어(토큰)로 자르는 렉서도 상태 기계다.
  • 네트워크. TCP 연결은 LISTEN, SYN-SENT, ESTABLISHED, TIME-WAIT 같은 상태를 오가는 상태 기계로 정의되어 있다.
  • 화면과 장치. 버튼의 보통·눌림·비활성 모양, 신호등, 자판기, 엘리베이터 제어가 모두 상태 기계다.
  • 계산 이론. 유한 상태 기계는 가장 단순한 계산 모델이다. 기억이 '지금 상태' 하나뿐이라 괄호 짝 맞추기처럼 끝없이 세어야 하는 일은 하지 못한다. 여기에 스택을 붙이면 푸시다운 오토마타, 무한한 테이프를 붙이면 튜링 기계가 된다.

상태가 수십 개로 늘어나면 비슷한 상태를 묶는 계층형 상태 기계나, 상태마다 객체를 하나씩 두는 상태 패턴으로 정리한다. 보리 정도의 캐릭터는 문자열 하나와 switch 문이면 충분하다.

State machines show up far beyond games.

  • Text processing. A regular expression can be turned into a state machine and run. The lexer that splits source code into tokens inside a compiler is one too.
  • Networking. A TCP connection is defined as a state machine that moves between states such as LISTEN, SYN-SENT, ESTABLISHED, and TIME-WAIT.
  • Interfaces and devices. A button's normal, pressed, and disabled looks, traffic lights, vending machines, and elevator controllers are all state machines.
  • Theory of computation. The finite state machine is the simplest model of computation. Its only memory is the current state, so it can't do anything that needs unbounded counting, such as checking that parentheses are balanced. Give it a stack and you get a pushdown automaton; give it an infinite tape and you get a Turing machine.

When states grow into the dozens, people group related states into a hierarchical state machine, or give each state its own object (the State pattern). A character like Bori needs no more than a string and a switch statement.

7.3보리의 상태 기계Bori's state machine

이제 보리를 상태 기계로 짜 보자. 보리가 있을 수 있는 상태는 서기, 달리기, 점프, 낙하, 비틀, 죽음의 여섯 가지다. 매 프레임 지금 상태에 맞는 일을 하고, 조건이 맞으면 다음 상태로 옮긴다. 화면을 클릭하고 보리를 움직여 보자. 아래 그림에서 지금 상태가 칠해지고, 방금 지나간 화살표가 빨개진다.

Now let's build Bori as a state machine. He can be in one of six states: idle, run, jump, fall, stumble, and dead. Every frame he does his current state's work and moves to the next state when its condition holds. Click the screen and move Bori around. The current state lights up in the diagram below, and the arrow just taken turns red.

모든 것을 상태로 만들 필요는 없다. 보리는 달리면서도 점프하면서도 도토리를 던질 수 있으니, 던지기는 상태가 아니라 12프레임짜리 타이머로 겹쳐 둔다. 동시에 일어날 수 있는 일은 같은 상태 기계에 넣지 않는 것이 기준이다.

Not everything needs to be a state. Bori can throw while running or jumping, so throwing is a 12-frame timer layered on top instead of a state. The rule of thumb: things that can happen at the same time don't belong in the same state machine.

7.4연출: 같은 게임, 다른 손맛Juice: same game, different feel

적을 맞힌 순간 세상을 4프레임 멈추는 히트스톱, 화면 흔들림, 튀는 파편, 착지할 때 찌그러지는 몸, 하얗게 번쩍이는 적, 떠오르는 점수. 하나하나는 작지만 다 끄면 같은 게임이 밋밋해진다. 아래 화면에서 도토리를 던져 적을 맞히며 하나씩 꺼 보자. 쓰러진 적은 잠시 뒤 다시 나타난다.

Hitstop that freezes the world for four frames when you land a hit, screen shake, flying debris, a body that squashes on landing, an enemy flashing white, a floating score. Each is small, but turn them all off and the same game goes flat. Throw acorns at the enemies below and switch the effects off one at a time. Defeated enemies come back after a moment.

7.5디버그 화면The debug view

보이지 않는 것은 고칠 수 없다. 히트박스, 타일 격자, 충돌 검사한 칸, 속도 벡터, 상태 이름을 화면에 덧그리는 스위치를 처음부터 만들어 둔다. 시간 배율을 0.25로 낮추거나 한 프레임씩 넘기면 '가끔' 일어나는 버그를 눈으로 잡을 수 있다. 위 화면 아래의 디버그 스위치를 켜 보자. 고정 타임스텝이라 느리게 돌려도 결과가 똑같다.

You can't fix what you can't see. Build switches from day one that draw hitboxes, the tile grid, the cells checked for collision, the velocity vector, and the state name over the screen. Slow time to 0.25× or step one frame at a time and you can catch the bugs that only happen "sometimes." Try the debug switches under the screen above. Thanks to the fixed timestep, slowing down doesn't change the outcome.

7.6비트맵 폰트A bitmap font

점수판 글자는 폰트 파일이 아니라 5×7 비트 그림을 모은 것이다. 글자 그림을 아틀라스 한 장에 늘어놓고, 문자열을 돌면서 해당 위치를 잘라 6픽셀 간격으로 찍는다. 이 페이지 각 장의 번호도 같은 폰트로 그렸다.

The scoreboard letters aren't a font file. They're a set of 5×7 bit pictures. The glyphs are laid out on one atlas, and drawing a string means cutting each glyph out of the atlas and stamping it 6 pixels apart. The chapter numbers on this page use the same font.

7.7장면과 저장Scenes and saving

게임 전체도 작은 상태 기계다. 타이틀 → 준비 → 플레이 → 죽음 → (목숨이 남으면) 준비, 아니면 게임 오버 → 타이틀. 골에 닿으면 클리어 장면에서 남은 체력을 점수로 바꾼다. 장면마다 업데이트와 그리기를 따로 둔다. 최고 점수처럼 다음에도 남아야 하는 값은 브라우저 저장소에 적는다. 사적인 창에서는 저장이 실패할 수 있으니 항상 실패를 감싼다.

The game as a whole is a small state machine too: title → ready → play → dying → ready again if lives remain, otherwise game over → title. Reaching the goal leads to a clear scene that converts the remaining vitality into points. Each scene has its own update and drawing code. Values that must survive until next time, like the best score, go into browser storage, and every write is wrapped in a try block because saving can fail in a private window.
